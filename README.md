# Proved specifications and loop invariants as Harbor tasks

Eighty-seven [Harbor](https://docs.harborframework.com/tasks/overview) tasks in which an
agent must **write a formal specification and prove it**, or **find the loop invariant that
closes a proof**, against a formal semantics of a Python subset — in two toolchains, the
[K framework](https://kframework.org) (`kprove`) and [Lean 4](https://lean-lang.org). Every
task has a machine-checked reference solution (the oracle), a verifier that cannot be
satisfied by a weaker claim, and no network access. The tasks are generated from the
machine-checked corpus in [`corpus/`](corpus/README.md) and regenerated by CI, so they
cannot drift from it.

```
harbor run --repo nlp-research-rosu/sample-data-public -d loop-invariants -a <agent> -m <model>
harbor run --repo nlp-research-rosu/sample-data-public -p tasks -i 'k-spec-*' -a <agent> -m <model>
harbor run -p tasks -a oracle          # local clone: every task scores 1
harbor run -p tasks -a nop             # local clone: every task scores 0
```

## The four task families

| family (registry name) | tasks | the agent gets | the agent writes | the verifier accepts iff |
|---|---|---|---|---|
| `k-proved-specs` — `tasks/k-spec-*` | 33 | the program, the K semantics, a `spec.k` skeleton with the entry claim's left-hand side (program AST, initial configuration, precondition) | the final scope map (every variable pinned to a closed form of the symbolic inputs), the `ensures` clause, and the circularity claims any loop needs | whitelist grammar · frozen regions unchanged · the pinned values agree with CPython on random inputs and each is determined uniquely · `kprove` prints `#Top` |
| `k-loop-invariants` — `tasks/k-inv-*` | 21 | the same, with the **complete entry claim** (postcondition included) frozen | the loop-invariant claims (one `#while`/`#loop`-anchored circularity per loop level) | whitelist grammar · entry claim unchanged · ≥ 1 extra claim · `kprove` prints `#Top` |
| `lean-proved-specs` — `tasks/lean-spec-*` | 12 | the klean-translated semantics, the reachability-logic calculus (`RL.lean`), the **proved** ∀-quantified path theorems of the program, the frozen claim with `sorry` | the derivation: Case Analysis + Consequence over the paths, packing the existential witnesses | `lake build` · a verifier-owned check file restates the claim and closes it with the agent's theorem · `#print axioms` lists only the five allowed axioms |
| `lean-loop-invariants` — `tasks/lean-inv-*` | 21 | the same, with the **proved execution legs** of the loop (prologue, one iteration, exit, epilogue) and the frozen claim with `sorry` | the invariant as a pattern and the Circularity derivation that composes the legs | same as above |

The programs are the 31 problems of the [KleverBench](https://github.com/nlp-research-rosu/KleverBench)
IMP seed set ported to a Python subset ([`programs/PROVENANCE.md`](programs/PROVENANCE.md);
five structural tiers from straight-line dataflow to nested loops and pipelines) plus the
original `abs_val`, `range_loop` and `sum_to_n` samples. The registry also exposes
`proved-specs`, `loop-invariants` (both toolchains) and `all`.

Difficulty is tagged, not calibrated: every `task.toml` carries `metadata.tier` (1–5, the
KleverBench structural tier), `metadata.loops`, `metadata.loop_depth`, `metadata.family`
and `metadata.toolchain`, plus a coarse `difficulty`. Expect the tier-1 K spec tasks to be
solved by every attempt of a strong model and the Lean loop tasks (hundreds of lines of
klean-term reasoning) by almost none; the point of the spread is that a pass@8 calibration
run can select the band it wants. Nothing here has been calibrated against a model.

## Anatomy of a task

```
tasks/k-inv-kb-sum/
├── instruction.md            what the agent is told (program, files, grading rules, a K primer)
├── task.toml                 Harbor config + metadata; separate verifier; no network; artifacts
├── environment/
│   ├── Dockerfile            K 7.1.337 image → kompile the semantics (shared layer) → /app
│   ├── klever/               the vendored klever MPY semantics + MPY-VERIFICATION module
│   └── app/                  program.py, verification.k, spec.k (the skeleton)
├── tests/
│   ├── test.sh → grade.py    the grader (stdlib Python, `python3 -I`, pristine verification.k)
│   ├── kclaims.py            claim parser / whitelist / closed-form evaluator
│   └── reference.json        frozen regions, inputs, precondition, program text
└── solution/
    ├── solve.sh              copies the reference spec.k into /app
    └── spec.k                the corpus claim module (kprove #Top)

tasks/lean-inv-kb-sum/
├── environment/
│   ├── Dockerfile            ubuntu → elan + Lean v4.30.0 → base package built (shared layer) → task files
│   ├── base/                 lakefile, toolchain, KMiniPy/{Prelude,Sorts,Inj,Func,Rewrite,Relations,RL}.lean
│   └── task/                 KMiniPy.lean (root), Verification/C14KbSumLegs.lean (proved legs), Verification/C14KbSum.lean (stub)
├── tests/
│   ├── test.sh → grade.py    restores verifier-owned files + pristine build dir, lake build, Check.lean, axiom audit
│   ├── Check.lean            the frozen statement over verifier-owned init/final, closed by the agent's theorem
│   └── pristine/             every verifier-owned source file
└── solution/C14KbSum.lean    the corpus derivation (proved; core axioms + two String-hook axioms)
```

Verifiers run in a **separate** copy of the environment: only the declared artifacts
(`/app/spec.k`, or the agent's `/app` tree minus `.lake`) are carried over, every
verifier-owned file is restored from the verifier's own copy, and the kompiled definition /
pristine Lean build directory come from the image. `network_mode = "no-network"` keeps the
agent from fetching this public repository, which contains every solution.

What the verifiers refuse, by construction:

- **K.** Anything but `requires "verification.k"`, one module importing
  `MPY-VERIFICATION`, and `[all-path]` claims: no `rule`, `syntax`, `[trusted]`,
  `[simplification]`, extra `imports`/`requires`. The entry claim's frozen regions are
  compared modulo whitespace and comments. In the proved-spec family the final scope must bind
  every variable the program assigns, every `?`-variable must be bound directly to a variable,
  the terms must evaluate (K integer semantics: `/Int` truncates) to CPython's final values on
  24 random inputs satisfying the precondition, and `ensures` must turn false under any
  perturbation of a `?`-variable — so `ensures true` or a disjunction of candidates is not a
  specification. Then `kprove` must print `#Top`.
- **Lean.** The check file re-declares `pre`/`post` over the verifier-owned `init`/`final` and
  proves the frozen statement by the agent's theorem (a changed statement is a type error);
  `#print axioms` must list nothing beyond `propext`, `Classical.choice`, `Quot.sound`,
  `eqStringHook` and klean's signature-only String-equality symbol — `sorryAx`,
  `Lean.ofReduceBool` (`native_decide`) or any added axiom fails.

`scripts/harbor/check_tasks.py` exercises the K graders offline (reference solutions pass
every step but `kprove`; untouched skeletons, `[trusted]`, lemma rules, extra imports,
`ensures true` and modified entry claims are rejected) and checks that no agent-visible
file contains a reference circularity or postcondition.

## Regeneration and checking

```
make harbor-tasks        # regenerate tasks/ + registry.json from corpus/ (idempotent)
make harbor-check        # drift check, shape, offline K graders, leaks, harbor lint
make harbor-oracle-lean  # Docker: harbor run -a oracle / -a nop on the Lean tasks
make harbor-oracle-k     # Docker: the same on the K tasks (kompile once, ~5 min)
```

[`.github/workflows/harbor.yml`](.github/workflows/harbor.yml) runs all of it on every push:
the pure-Python checks and lint, `lake build` of the whole Lean corpus, and the oracle/nop
runs for both toolchains. The generator is
[`scripts/harbor/build_tasks.py`](scripts/harbor/build_tasks.py); the templates it renders are
in [`scripts/harbor/templates/`](scripts/harbor/templates/); the claim library shared by the
generator and the K graders is [`scripts/harbor/kclaims.py`](scripts/harbor/kclaims.py).

## The corpus behind the tasks

Everything the tasks hand out or check against is a machine-checked record in
[`corpus/`](corpus/README.md): 34 `kprove` verification records (33 proved specs with their
loop invariants as circularity claims, one refutation with its counterexample run), the
Lean 4 package that re-derives each claim in reachability logic (`lake build` replays every
proof; `AxiomAudit.lean` prints the axioms under every theorem), the K claim modules, and
the concrete execution traces (a1–a4) and symbolic execution trees (b1–b2) over the same
semantics. The traces and trees are not tasks; they are training data of the kind code
models are mid-trained on (line-level execution states, here with the semantic rule behind
every step and with path conditions), and they remain validated by `make k-validate`.
[`REPORT.md`](REPORT.md) documents the corpus in detail: record schemas, generation,
validation, and the full regeneration recipe.

## Layout

```
tasks/           87 Harbor tasks (generated; implicit dataset for `harbor run -p tasks`)
registry.json    named datasets over tasks/ for `harbor run --repo ... -d <name>`
corpus/          the canonical, machine-checked source: k/ (records), lean/ (package), specs/ (K claims)
programs/        the Python subjects
semantics/       mpy-traced/ (klever MPY + trace overlay) and minipy-lean.k (klean-ready)
scripts/         harbor/ (generator, graders, checks), k/ and lean/ (corpus pipelines), py2mpy_traced.py
vendor/klever/   pinned upstream semantics (never modified)
docs/            historical plans and the klean feasibility experiment
```
